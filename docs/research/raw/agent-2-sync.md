## A. How a running timer is represented, and clock skew

1. [S] Toggl Track API v9: a running entry has a negative `duration` ("preferable -1"), `stop` is null, and `start` is UTC. `GET /me/time_entries/current` returns the running entry, and stopping it is a separate `PATCH .../time_entries/{id}/stop`. A stop on an entry that is already stopped is a documented error case ("Time entry already stopped"). https://engineering.toggl.com/docs/track/api/time_entries/ (n.d.) [toggl-time-entries.html]
2. [S] Toggl API v8 (old, archived) spelled the encoding out: for a running entry, `duration` holds minus the start time in epoch seconds, and the elapsed time is `current_time + duration`. The example has `"duration":-1391072884`. https://github.com/toggl/toggl_api_docs/blob/master/chapters/time_entries.md (archived, n.d.) [toggl-v8-time-entries-md.html]
3. [S] Toggl v9 says that if both `stop` and `duration` are sent, they must agree (`start + duration == stop`). Responses carry `at`, the last-update time in UTC. The `since` query returns "entries modified since this date … including deleted ones". Same URL as item 1.
4. [I] So the industry pattern is that a timer stores its start instant and state, never a ticking value. Every client computes `now - start` locally. Toggl has no pause, so pause is not covered by its model.
5. [S] Clockify stores entries in UTC. If the device clock or time zone shifts after a timer starts, the stop can land before the start and Clockify "prevent[s] you from saving it". Its fix is to tell the user to correct the device clock. https://clockify.me/help/troubleshooting/cant-stop-the-timer (n.d.) [clockify-cant-stop.html]
6. [S] Firebase RTDB exposes `/.info/serverTimeOffset`, the milliseconds a client adds to its local epoch time to estimate server time. The docs say latency affects its accuracy, so it is meant for "discovering large (> 1 second) discrepancies". They prefer the server-stamped `ServerValue.TIMESTAMP` for writes. https://firebase.google.com/docs/database/web/offline-capabilities (last updated 2026-11-18) [firebase-offline.html]
7. [S] HLC (Kulkarni et al.) combines a physical clock with a logical counter. It captures causality like a logical clock, stays close to NTP time, fits in a 64-bit NTP timestamp and is "masking tolerant to NTP kinks". https://cse.buffalo.edu/tech-reports/2014-04.pdf (2014) [hlc-paper.pdf]
8. [S] Actual Budget's clock is a "Hybrid Unique Logical Clock" based on that HLC paper. It is millis, a 16-bit counter and a 16-hex-character node id, serialised to a sortable 46-character string. It allows 5 minutes of drift (`maxDrift: 5*60*1000`) and throws `ClockDriftError` past that. https://github.com/actualbudget/actual/blob/master/packages/crdt/src/crdt/timestamp.ts (master as fetched 2026-11-24) [actual-src-timestamp.ts.txt]
9. [S] Actual's server also rejects messages whose timestamp is more than 5 minutes in the future ("clock-drift"). The code comment says "later messages break sync on other devices". https://github.com/actualbudget/actual/blob/master/packages/sync-server/src/sync-simple.js [actual-src-sync-simple.js.txt]
10. [S] Kingsbury (Jepsen): under last-write-wins (LWW) with wall clocks, a tombstone or write from a node whose clock runs ahead silently discards later writes, "for days to weeks" in the worst case. The recommended fixes are monotonic clocks, vector clocks or dotted version vectors, and never letting timestamps go backwards within a session. https://aphyr.com/posts/299-the-trouble-with-timestamps (2013-10-12) [aphyr-trouble-timestamps.html]
11. [S] Figma needs no timestamps for its LWW properties, "because the server can define the order of events". https://www.figma.com/blog/how-figmas-multiplayer-technology-works/ (2019-10-16) [figma-multiplayer.html]

## B. Documented behaviour when two devices change a timer (offline or concurrent)

12. [S] Toggl Focus API: on start, "If a running entry already exists it is automatically stopped and the new entry is returned." https://engineering.toggl.com/docs/focus/api/tracking/ (n.d.) [toggl-focus-tracking.html]
13. [S] Toggl Track v9 guide: starting is a POST with `duration:-1`, followed by "Don't forget to stop your running time entry!" It does not say what happens to an entry that is already running. https://engineering.toggl.com/docs/track/tracking/ (n.d.) [toggl-track-tracking.html]
14. [S] Toggl Track's web app enters offline mode automatically, but only on the Timer page. Unsynced entries show an exclamation icon, and data created or updated offline "will be synced … once your connection is restored". https://support.toggl.com/en-us/article/can-toggl-track-work-offline-4r4tcw/ (updated 06/16/2026) [toggl-can-work-offline.html]
15. [S] Toggl: unsynced mobile entries show a grey mark, failed ones a red mark. Mobile apps sync when opened after more than 5 minutes in the background. The help page warns users not to log out or refresh with unsynced entries, "to avoid losing the data". The desktop apps keep a local SQLite file that support can recover entries from. https://support.toggl.com/en-us/article/how-does-toggl-track-sync-data-12n5i7e/ (updated 07/24/2026) [toggl-how-sync.html]
16. [S] Clockify (iOS and Mac): the timer can be started or stopped and entries created offline. They are saved locally and synced automatically when back online. Projects, tags and similar cannot be created offline, and unsynced data is lost on logout. https://clockify.me/help/apps/mobile-app (redirects to the iOS page, n.d.) [clockify-mobile.html], https://clockify.me/help/apps/mac-app [clockify-mac.html]
17. [S] TickTick has an opt-in "Sync Across Devices" setting for Focus (Pomodoro). Start, pause and finish on one device apply on all others. The feature shipped on Jul 24 (2023 changelog). https://help.ticktick.com/articles/7055782010496745472 (n.d.) [ticktick-start-focus.html], https://help.ticktick.com/external/articles/7155128685119406080 [ticktick-updates-2023.html]
18. [S] Forest "Plant Together": a host creates a room, shares a code and starts it, and if anyone leaves the app "everyone's tree … die[s]". https://forestapp.cc/llms.txt (n.d.) [forest-llms.html], with the school guide at https://mycentennial.sd43.bc.ca/tech-leadership/files/2020/11/How-to-Use-Forest.pdf (Nov 2020) [forest-howto.pdf]
19. **Not found:** a documented rule from Toggl, Clockify, TickTick, Session or Forest for what happens when two offline devices both start, stop or pause the same timer and then reconnect, or whether overlapping offline entries are merged, kept or rejected. Each one documents only "offline entries sync later". Search snippets about Session and Flow were App Store reviews, not docs, so I did not use them.

## C. The main sync models, what they cost and what data they suit

**Server-authoritative op log with client rebase (Replicache, Linear, PowerSync, Todoist)**

20. [S] Replicache: clients run named mutators locally (speculative state) and push the mutations with per-client sequential ids. The server re-runs them as the authority. On pull the client rewinds to the last server state, applies the patch and replays its pending mutations ("rebase"). Conflict policy is arbitrary code in the mutators. https://doc.replicache.dev/concepts/how-it-works (n.d.) [replicache-how.html]
21. [S] Replicache: a pull returns a cookie, a patch and `lastMutationIDChanges`. The simplest cookie is one global version of the whole datastore. https://doc.replicache.dev/concepts/how-it-works
22. [S] Replicache supports offline use "for hours to days", but "the potential for serious conflicts grows the longer users are disconnected". It does not "always produce a resolution users would be happy with" and recommends history or undo for long offline use. https://doc.replicache.dev/concepts/offline (n.d.) [replicache-offline.html]
23. [S, third party] Linear's sync engine, reverse-engineered by wzhudev rather than published by Linear: the server executes client transactions and assigns a global, monotonically increasing `lastSyncId`, so the order is total, unlike a CRDT's partial order. Delta packets go to all clients, including the sender. Offline transactions are cached in IndexedDB and resent. A rejected transaction rolls back on the client. Pending UpdateTransactions are rebased onto incoming deltas with LWW, and only UpdateTransactions get conflict handling. https://github.com/wzhudev/reverse-linear-sync-engine (last commit 2025-06-02) [reverse-linear.html]. Linear's own talk is video only: https://linear.app/now/scaling-the-linear-sync-engine (2023-06-29) [linear-scaling-sync.html]
24. [S] PowerSync: client mutations go into an ordered upload queue, drained against a backend endpoint you write. The client does not advance to a new server checkpoint while it has queued mutations, "so the client never has to resolve conflicts locally". The simplest backend gives per-field LWW "as received by the server". https://docs.powersync.com/architecture/consistency [powersync-consistency.html], https://docs.powersync.com/handling-writes/handling-update-conflicts (n.d.) [powersync-conflicts.html]
25. [S] Todoist Sync API: commands are batched in one HTTP POST. Each command carries a client-generated `uuid`, and the server "will not execute a command that has same UUID as a previously executed command", so retries are safe. Creates carry a `temp_id`, and the response returns `temp_id_mapping` and per-command `sync_status`. Reads are incremental via `sync_token` (`*` means full sync). Resources have `is_deleted`. Command errors with HTTP 400 are terminal and must not be retried. https://developer.todoist.com/api/v1/ (n.d.; the old `/sync/v9/` URL now serves this page) [todoist-api-v1.html]
26. **Not found:** any Todoist documentation of how it resolves two commands that edit the same field.

**Per-field LWW with HLC timestamps (Actual Budget, Figma's variant)**

27. [S] Actual: every change is a message `(timestamp, dataset, row, column, value)`. On receipt, a message is applied only if no later timestamp exists for the same cell. Older ones are marked "old", not applied, but still enter the merkle trie. https://github.com/actualbudget/actual/blob/master/packages/loot-core/src/server/sync/index.ts [actual-src-index.ts.txt]
28. [S] Actual's server is a blind relay. Per budget file it keeps one SQLite file with `messages_binary(timestamp PK, is_encrypted, content)` and one merkle row. Sync is `INSERT OR IGNORE` of incoming messages and a return of `WHERE timestamp > since`. The content can be end-to-end encrypted. [actual-src-messages.sql.txt], [actual-src-sync-simple.js.txt]
29. [S] Actual compares a merkle trie of timestamps with the server and loops until in sync (capped at 100 passes). Without a stored sync point it syncs from "5 minutes ago". [actual-src-index.ts.txt]
30. [S] Actual stores every mutation, so the file grows. "Reset sync" compacts it and makes every other device revert, and any unsynced changes on other devices are lost. Actual says simultaneous edits "should work unless the edits conflict. To be safe, avoid simultaneous usage". https://actualbudget.org/docs/getting-started/sync/ (n.d.) [actual-sync-docs.html]
31. [S] The design comes from James Long's "CRDTs for Mortals": HLC timestamps plus a merkle tree to check that clients agree. https://github.com/jlongster/crdt-example-app (dotJS 2019) [jlongster-crdt-example.html]
32. [S] Figma: the document is `Map<ObjectID, Map<Property, Value>>`. The server keeps the last value received per (object, property). Concurrent edits to different properties never conflict, and same-property edits resolve to whichever reached the server last. A client discards incoming server values that conflict with its own unacknowledged edits, to avoid flicker. After an offline period the client downloads a fresh copy and reapplies its offline edits on top. Object ids embed a client id so they can be created offline. Ordering uses fractional indexing, with parent and position stored as one atomic property. [figma-multiplayer.html]

**Full CRDT documents (Automerge, Yjs)**

33. [S] Automerge: for concurrent writes to one property, every replica picks the same winner deterministically. The losing values are kept and exposed through `getConflicts()` (LWW plus a multi-value register). "Last" means operation id order (counter, then actor id), not wall-clock time. https://automerge.org/docs/reference/documents/conflicts/ (n.d.) [automerge-conflicts.html]
34. [S] Automerge `Counter`: concurrent increments add up, where a plain number would lose them (3, then two concurrent +1, gives 4 instead of 5). Automerge advises UUIDs, not auto-increment ids. https://automerge.org/docs/reference/documents/counters/ [automerge-counters.html]
35. [S] automerge-repo storage keeps incremental changes and snapshots keyed by `[docId, type, heads|hash]`. Compaction is "crucial to make the approach of storing every change … feasible". https://automerge.org/docs/reference/under-the-hood/storage/ [automerge-storage.html]
36. [S] Ink & Switch on cost: "CRDTs accumulate a large change history, which creates performance problems", and that history can't easily be truncated because a peer may reconnect "after six months". https://www.inkandswitch.com/essay/local-first/ (April 2019) [inkswitch-localfirst.html]
37. [S] Yjs: `doc.gc` (garbage collection) is on by default. Setting it false keeps old content so it can be restored. https://docs.yjs.dev/api/y.doc [yjs-ydoc-gc.html]
38. [S] Kleppmann: CRDTs "are easy to implement badly. Many published algorithms have anomalies … Simple implementations often have terrible performance". https://martin.kleppmann.com/2020/07/06/crdt-hard-parts-hydra.html (2020-07-06) [kleppmann-crdt-hard-parts.html]
39. [S] The Figma and Linear sources both say CRDTs are built for decentralised systems and carry metadata overhead that a server-centred app can drop. [figma-multiplayer.html], [reverse-linear.html]

## D. Deletes, same-field conflicts, and keeping history

40. [S] Ink & Switch: a CRDT merges everything except concurrent updates to the same property of the same object. There it "keeps track of the conflicting values" for the app or user to resolve. In their prototypes such conflicts were rare, and the default merge rules were always enough. [inkswitch-localfirst.html]
41. [S] Ink & Switch: Dropbox makes "conflicted copies" and Evernote moves notes to a "conflicting changes" notebook. Both leave the merging to the user. [inkswitch-localfirst.html]
42. [S] ElectricSQL quotes Adam Wiggins (Muse, 2023): in practice "conflicts are extremely rare and can be mitigated well by strategies like presence". For a rejected offline write, its options include "marking local writes as rejected and displaying for manual conflict resolution". https://electric-sql.com/docs/guides/writes (n.d.) [electric-writes.html]
43. [S] Figma: deletes remove all of an object's data on the server. The deleting client keeps the properties in its undo buffer so it can restore them. [figma-multiplayer.html]
44. [S] Actual: deletes are soft, as a `tombstone` column on the row set by an ordinary LWW message, and queries filter `tombstone = 0`. https://github.com/actualbudget/actual/blob/master/packages/loot-core/src/server/db/index.ts [actual-src-db-index.ts.txt]
45. [S] PowerSync names "one client deletes the record while the other updates it" as a conflict case that the backend must handle. [powersync-conflicts.html]
46. [S] Todoist (`is_deleted`) and Toggl (`since` includes deleted entries) both send deletions to clients as flags on records. [todoist-api-v1.html], [toggl-time-entries.html]
47. [S] Kingsbury: LWW tombstones from a clock running ahead silently delete later writes (item 10).
48. [I] Only append-only creation keeps offline history intact by construction. A focus session recorded offline is a new record with a client-generated id (Figma, Automerge and Todoist all generate ids on the client), so there is nothing to collide with. LWW only loses data when two writers touch the same mutable field.

## E. Real-time transport and catch-up

49. [S] Figma uses WebSocket, with one server process per document. On reconnect it downloads the full document and replays local edits. [figma-multiplayer.html]
50. [S, third party] Linear uses a WebSocket for delta packets. In the handshake the client compares its local `lastSyncId` with the server's and fetches the deltas it missed. [reverse-linear.html]
51. [S] Replicache sends a contentless "poke" over SSE or WebSocket to trigger a pull. Its todo starter app uses SSE, and the timed `pullInterval` is "really only used in development". [replicache-how.html]
52. [S] Electric delivers HTTP log reads with an `offset` cursor and a `handle`. Live mode is long-poll, with SSE optional (`live_sse=true`). SSE means fewer requests and lower latency, but it breaks behind proxies that buffer. Long-poll copes better with restrictive proxies and caching. https://electric-sql.com/docs/api/http (n.d.) [electric-http-api.html]
53. [S] Actual syncs by binary HTTP POST to `/sync`, sending messages since the last timestamp, then reconciles with a merkle diff. A full sync is scheduled with `FULL_SYNC_DELAY = 1000` ms. Nothing in this file shows a server push channel. [actual-src-index.ts.txt]
54. [S] Todoist: HTTP POST with a `sync_token` cursor. No WebSocket or push is documented on that page. [todoist-api-v1.html]
55. [S] Yjs awareness (presence) lives outside the document as a small state-based CRDT and is deleted when a client goes offline. In y-protocols, a peer is dropped after `outdatedTimeout = 30000` ms without renewal, and each client renews every 15 s. https://docs.yjs.dev/getting-started/adding-awareness [yjs-awareness.html], https://github.com/yjs/y-protocols/blob/master/src/awareness.js [yprotocols-awareness-js.html]

## F. Small self-hosted precedents and resource use

56. [S] Actual (official docs): on PikaPods, "leave the resources at their lowest setting". The browser does most of the computation, it costs about $1.50 a month (Nov 2025), and about 33 MB stores 1,200 transactions over 18 months. https://actualbudget.org/docs/install/pikapods [actual-pikapods.html]
57. [S, third party] A Railway template guide says Actual's server needs 512 MB minimum and 1 GB recommended, and that "idle memory sits under 100 MB" because it "mostly stores and relays sync messages". https://railway.com/deploy/actual-budget-railway.md (n.d.) [railway-actual.html]. This is not an official measurement, and I found no official RAM figure.
58. [S] Zero (Rocicorp) needs zero-cache (view-syncers plus a replication-manager), Postgres with `wal_level=logical`, and your own API server. The minimal example sizes zero-cache at 1 vCPU and 2 GB. https://zero.rocicorp.dev/docs/self-host.md (n.d.) [zero-self-host-md.html]
59. [I] Zero by itself exceeds a 1 GiB box. PowerSync and Electric also need a separate sync service in front of Postgres (from their architecture pages). I did not measure them, and I found no official RAM figures for either.

## G. Sources that conflict

- Toggl: the Focus API auto-stops a running entry on start (item 12), but the Track v9 guide does not and tells you to stop it yourself (item 13). These are different products, and I found no Track rule. A search snippet cited a "Toggl offline mode" help page that says offline mode must be enabled by hand. That URL now returns 404 (https://support.toggl.com/toggl-offline-mode/), and the live page says it is automatic (item 14).
- LWW ordering source: Figma, PowerSync and Linear order by arrival at the server (items 11, 23, 24). Actual orders by client HLC timestamp (item 27). Automerge orders by operation counter and actor id, not wall-clock time (item 33). These are different meanings of "last", not factual conflicts.

## H. What this implies for a timer app (all inferred)

- Model a timer as an append-only event log per account: `{id: client UUID, device, kind: start|pause|resume|stop, at: device time corrected by server offset, hlc}`. Derive the state (running, paused, accumulated) by folding the events. Never sync a ticking value (items 1-4, 8).
- Store each finished focus session as its own immutable record with a client-generated UUID (item 48). Two offline devices then produce two sessions and nothing is lost. Show overlaps to the user instead of merging them silently. No product documents a rule for this, so it is your call (item 19).
- For the single "current timer" slot, use server-arrival LWW, as Figma, Linear and PowerSync do. It needs no clock trust, and losing a start or stop race is harmless when every session is also logged. If you sort by client time, use HLC with a drift cap and server-side rejection as Actual does, or a skewed phone can override real actions (items 8-10).
- Correct displayed elapsed time with a server time offset (Firebase-style, item 6). Clamp negative durations rather than refusing to stop the timer as Clockify does (item 5).
- Tasks: per-field LWW with soft-delete tombstones (Actual, Figma). A same-field clash on a title is rare (items 40, 42). Keep the losing value in a history row if you want to undo it.
- Habit check-ins: make each one an idempotent row keyed by (habit, date, device or UUID), or a counter CRDT. Never read-modify-write an integer (item 34).
- Ordered lists: a fractional index stored as a single LWW field (Figma, item 32). A sequence CRDT is not needed.
- Server: a blind, append-only relay with a cursor (Actual's `timestamp > since`, Todoist's `sync_token`, Linear's `lastSyncId`), idempotent command UUIDs (Todoist), plus one WebSocket or SSE channel for pokes and presence. Of the precedents found, this is the smallest (Actual, under 100 MB idle per the third-party figure, items 28, 57). Full CRDT documents (Automerge, Yjs) and Zero, PowerSync or Electric add history growth or a second service (items 35, 36, 58).
- Study-group live focus is ephemeral presence: keep it out of the synced store and expire it on a timeout, as Yjs awareness does (30 s, item 55). If it is lost there is nothing to resolve.
